# ReadyMeet lint policy

## Source and execution

This policy ports the local `lint-ddd/tooling` reference and Codely 4.5.0, with the user-approved exclusion of all Tailwind-related rules. `tooling/{boundary,convention,presentation,validation}Rules.ts` contain the copied custom rules. `tooling/eslint.rules.ts` contains the reference general, strict type-aware and JSX rules. All enabled rules are errors. Dependencies are pinned in the root manifest and lockfile; no reference checkout is needed at runtime. Jiti loads the TypeScript rule modules on Node 22 without relying on native TypeScript stripping.

`pnpm lint` checks all authored JavaScript and TypeScript, including add-ons, deployment wrappers, tests, scripts, configs and tooling, with zero warnings. Only dependency directories and generated build/cache output are ignored. The same generated-output patterns are given to the boundary plugin, so imports of ignored output remain errors even inside a classified layer. TypeScript uses the root lint-only project, including workspace source and alias resolution. JavaScript uses a typed parser for custom source rules; Codely's JavaScript rules still apply. Reference strict TypeScript rules remain scoped to TypeScript, not silently imposed on untyped JavaScript. MTS/CTS receive both Codely's typed rules and the reference strict/custom rules. Formatting is double quotes, semicolons, trailing commas, 120 columns, two spaces for TypeScript and Codely's tabs for JavaScript. Folder names also allow hyphens because ReadyMeet's existing package/deployment names use them.

## Roles

The role table applies independently within every package at the repository root (`web`, `api`, `assistant`, `db`, `shared`, and `openai-responses`):

| Caller             | Allowed local dependencies                                          |
| ------------------ | ------------------------------------------------------------------- |
| Domain             | Domain                                                              |
| Ports              | Domain, ports                                                       |
| Application        | Domain, ports, application                                          |
| Primary adapters   | Domain, ports, application, composition; the same adapter           |
| Secondary adapters | Domain, ports; the same adapter                                     |
| Composition        | Domain, ports, application, primary/secondary adapters, composition |
| Presentation       | Domain, presentation, composition                                   |
| Tests and tooling  | Required roles and external modules                                 |

Implementation roles live in `{domain,ports,application,composition,presentation}` and `adapters/{primary,secondary}/<adapter>` at the package root. Element identity captures package and adapter: an adapter with the same name in another package is **not** the same adapter. Boundaries checks import, export, require, dynamic import, type import and import-equals. Both the import plugin and boundaries resolve TypeScript aliases to actual files. Workspace imports are never allowed as an undifferentiated external namespace.

The database public `db/index.ts` is a composition facade. Application cannot import `@readymeet/db`, its concrete adapter subpaths, or a relative/alias equivalent. Exactly `db/ports/repository.ts` may use type-only dependencies on that facade and the PostgreSQL `ashby.ts`, `meeting-call-in-lock.ts`, `repositories.ts`, `relationship-memory.ts`, and `slack-review.ts` owners. It derives `RepositoryPort` from the assembled implementation and reexports consumed implementation-owned types; the calendar prep result alias follows the actual query projection rather than the full table row. Shared meeting-context input and join-request domain types remain independent to avoid recursive inference. This exception permits no runtime imports, neighboring port files, unrelated adapter files, or direct application-to-implementation type imports. Tests check both the narrow boundary and that the facade and its service port consumers load without database initialization. Shared `shared/index.ts` is a domain facade and must not reexport outward-owned implementation. Internal subpaths retain their resolved roles, including ports and adapters across package boundaries. Unknown source and dependencies on unknown or ignored source are errors. `@readymeet/openai-responses` is the shared secondary adapter for OpenAI responses calls. The assistant `openai` secondary adapter may import that package. Other secondary adapters and inward roles may not. Composition may import it under the existing composition rule. The Vercel AI SDK stays in that adapter.

Tests (`*.test.*`, `*.spec.*`, `tests/**`) and tooling are classified first with exclusive file categories, including colocated tests. Internal edges are checked as well: product code cannot import a colocated test or config and inherit its unrestricted dependencies. Test/tooling callers retain reference freedom. Tooling consists of `tooling/**`, configuration files, package-root build/diagnostic `scripts/**`, the Outlook manifest/build formatter and Next's generated type entrypoint. **Product `scripts/**` outside those build wrappers is not tooling** and must be placed in the appropriate implementation role. The Outlook browser bundles in `web/public/outlook/{core,commands,meeting-flow,taskpane,dialog,command-error}.js` are esbuild output of the TypeScript roles and are ignored as generated files. `web/public/outlook/calendar-description.js` stays a formatted transpile of `shared/domain/calendar-description.ts`.

Framework-required files have explicit classifications, not blanket folder exemptions:

- `web/app/**/*.tsx`: presentation (thin Next entrypoints).
- `web/app/**/route.ts`: primary `next-http`, including calls into that package's `adapters/primary/next-http`.
- `web/public/outlook/**`: primary deployment adapter, not presentation or tooling.
- `web/adapters/primary/google-calendar/Code.js`: primary Google Apps Script deployment entrypoint.
- Exactly `web/auth.ts`: composition, restricted to a thin server-only auth reexport facade.
- Exactly `web/middleware.ts`: primary Next `next-http` framework entrypoint. Generic primary directions remain unchanged; adapter delegation is limited to this package's matching `next-http` adapter, never unrelated adapters. Next statically analyzable config/matcher may remain locally; the web owner preserves session revocation behavior. No neighboring `src` allowance.
- Exactly `api/index.ts` and `api/memory-worker-entry.ts`: composition, conditional on genuine thin delegates to relocated composition operations. Preserve existing source/dist entrypoints and public commands; API owner verifies behavior and runtime lifecycle. No new external permissions, neighboring source classification or generic `src` allowance; inward roles cannot import these composition files.
- Exactly `assistant/index.ts`: composition bootstrap. Only this file may import `openai/shims/web`; other composition paths still cannot import that shim or the OpenAI SDK. The assistant owner must preserve and test shim-first runtime ordering.

Exactly `db/migrate.ts` and `db/seed.ts` are also composition files, classified by explicit paths before generic role patterns. These stable operational entrypoints must remain thin delegates to relocated composition/CLI operations, with only exit-code/stderr mapping. No pg/Prisma imports, SQL or business logic belongs in the entrypoints. Their classification uses the existing composition rules and external allowlist unchanged; it is not a `db/**` or migration-directory exception. Neighboring source remains unknown unless independently classified. Keep the public migrate/seed commands; do not run them against a database during migration verification.

### Backend initialization and direct operation imports

API and assistant entrypoints finish initialization with awaited imports before loading `composition/server.ts`. API initialization retains dotenv precedence, repository/realtime registration, provider wiring, schema validation and production-secret checks. Assistant loads `openai/shims/web` first, then completes `composition/wire.ts` before evaluating routes and their top-level environment reads. Tests and operational scripts that use those services load initialization explicitly; the API test command retains its preload. Configuration and security/provider ports remain; export-only composition bridges do not.

The same-service `http` primary adapters may import only the explicit secondary operation files listed in `tooling/architecture.mjs`. These are operations previously reached through export-only composition modules, not permission to import arbitrary adapters or vendor SDK packages. API operations cover the listed Ashby, Jose, LiveKit, secret-crypto, Slack, Stripe and assistant-client files; assistant operations cover its three LiveKit manager/event files. Domain, ports, application, other primary adapters and other packages retain their restrictions. Positive and negative boundary tests cover the exception; startup tests execute both real entrypoints with dummy configuration and reject missing, invalid and insecure production settings without querying a database or calling providers.

Those classifications do not certify that a wrapper is thin; implementation ownership still requires review. Other unclassified framework files must be moved behind, or explicitly assigned to, a legitimate role rather than ignored.

API application code may import `node:crypto`, `node:dns/promises`, `node:fs/promises`, `node:net`, `node:os` and `node:path` directly. Assistant application code and the API `http` primary adapter may import `node:crypto` directly. Exactly `api/composition/a-configure.ts` may import `node:path` and `node:url` for environment-file resolution. These are standard-library calls, not provider bindings: no Node runtime port or registration is required. The existing environment loaders and provider/repository wiring remain responsible for initialization; removing Node registration does not change their order, precedence or validation.

These permissions match the backend workspace/package and role (plus the API HTTP adapter identity), or the exact configuration file, and the full `node:` specifier. They do not allow bare built-in names, unrelated Node modules, provider SDKs, browser application/presentation code, domain code, ports or other composition files. Existing secondary-adapter permissions are unchanged. Boundary tests cover both allowed consumers and these forbidden neighbors.

Installed Next normalizes `next/headers` and `next/server` to package source `next`. Those two full dependency sources are permitted only from `web/adapters/primary/next-http/**` and exact matching framework entrypoints `web/app/**/route.ts` and `web/middleware.ts`. This is not a package-wide Next allowance: root `next`, other subpaths, unrelated/cross-package primary adapters and inward roles remain denied. Regression tests resolve the actual installed Next package and reject unresolved imports.

Google Apps Script globals (`ScriptApp`, `PropertiesService`, `UrlFetchApp`, `CacheService`, `ConferenceDataService`, `CardService`, `Utilities`) and Outlook `Office` are explicitly readonly in their JavaScript deployments; undefined-name checking remains enabled. Exactly `web/adapters/primary/google-calendar/Code.js` uses `sourceType: "script"` and also has the readonly `ReadyAddon` global for thin wrappers around the approved minimal bundled ESM deployment. This remains the single `ReadyAddon` global; `Implementation.js` is produced by minimal build-time aggregation of actual role entries, with no global rename. The five actual global handlers use a standard `/* exported ... */` declaration; unused local bindings still fail. No sibling file receives this global or script mode; implementation ESM files remain modules. The add-on owner supplies its manifest/build wrapper changes; its runtime `zod` (`^3.24.3`, locked to existing `3.25.76`) and development `esbuild` (`0.27.7`) are the only additional importer entries. Consumer frozen installs require that updated add-on-owned manifest together with the lock update.

An allowed dependency is not permission to move business logic into a framework layer. Ambient `fetch`, `Date`, `Math.random`, browser and Apps Script globals are not an import boundary; review must ensure core logic receives those effects through ports.

## Shared conventions

- Const-only declarations; no loop statements or non-null assertions; literal dependency specifiers; explicit caught errors; async/await rather than promise chains.
- Complexity at most 15, nesting at most 4, functions at most 100 nonblank/noncomment lines. Import cycles, unused bindings and unsorted imports are errors.
- Strict type-aware safety, type-only imports/exports, array syntax and strict boolean expressions.
- Boolean names use `is`/`has`/`can`/`should`. Authored multiargument functions use named parameter objects, retaining reference exceptions for external signatures and annotated external protocol fields. Public wire fields must not be renamed to appease the rule.
- Explicit empty-array comparisons, immutable array transformations and no parameter mutation.
- Named source messages/errors and numeric constants; JSON input validation through concrete Zod schemas. Unknown/any schemas do not establish validation.
- Annotated `@nullable` optional domain/port fields explicitly include null, across all packages.
- Unrelated JSX layout/prose restrictions, accessible native controls and ternaries remain in force. Existing CSS/CSS Modules, inline styles and dynamic CSS custom properties are allowed.
- Unused authored React props are checked in package `presentation` and web Next app TSX, including declarations at those paths.
- TODO comments use `TODO(cleanup):` plus a reason; literal log messages end with periods.
- Prefer the simplest persistence operation that preserves correctness. Use ordinary Prisma queries when they express the operation clearly. Transactions, row locks, Prisma SQL expressions, and parameterized SQL are allowed when needed for atomic changes, concurrency safety, or a clearer query. Never concatenate untrusted values into SQL. Keep database mechanics in persistence adapters; domain code must remain database-independent. Tests may use database queries and locks to prove failures and concurrent behavior. Do not add a transaction, wrapper, or query framework without a concrete need. This is a code-review standard, not a blanket syntax ban; the former `policy/no-raw-sql` rule is removed. Other lint, validation, and architectural-boundary rules remain unchanged.

## User-approved CSS policy difference

The user explicitly excludes Tailwind and all Tailwind-related lint rules. `policy/static-tailwind` is not registered or configured; its margin, even-spacing and redundant-breakpoint analysis and helpers are removed. The JSX `style` ban that mandated Tailwind and the `className` margin/even-spacing selectors are also removed, without a replacement inline-style ban. Plain CSS and CSS Modules keep their current naming, file placement, tokens, selectors and responsive patterns. Inline styles and dynamic CSS custom properties remain allowed. Do not introduce Tailwind, utility-first styling, CSS-in-JS or another styling dependency/system. This deliberate policy adaptation does not change unrelated general, strict TypeScript, boundary, JSX, accessibility or used-React-props enforcement.

## Exact assistant native Console dependency

Only `assistant/adapters/secondary/observability/logger.ts` may import `node:console`. The policy matches the exact file/full specifier and core module source; bare `console`, neighboring observability files, other adapters/packages and application/domain/ports/composition receive no new permission. This permits native `Console` construction with injected stdout/stderr streams, not a global console bypass or a hand-written formatter. Assistant owns the typed logger port and stream/TTY/error behavior tests.

A pre-edit real-config experiment confirms imported native `Console` instance methods are not rejected by `no-console`; no source-provenance workaround or suppression is needed or added. Existing `no-console` remains an error with its original `error` method allowance: global `console.log` still fails, while native `logger.log`/`logger.error` pass with native construction. Literal log-message punctuation remains enforced. Policy regressions prove the exact dependency permission, surrounding negatives, lint-clean native constructor/method calls and unchanged global/message checks; they do not claim runtime equivalence for product code.

## Exact web browser query-cache dependency

`@tanstack/react-query` is permitted from the captured secondary adapter `web/adapters/secondary/browser-query-cache/**` only. The rule matches the exact package specifier and the web workspace/package/adapter identity; it adds no general secondary permission or package-subpath allowance. Domain/application/ports, other adapters (including similar names), primary origins and another package's identically named adapter remain denied. Existing presentation/composition permissions are unchanged. Real-policy tests exercise top-level/nested adapter files and surrounding negatives with actual dependency resolution. No product source, manifests or dependency versions change.

## Exact API memory subprocess dependency

Only `api/adapters/secondary/memory-process/child-process.ts` may import `node:child_process`. The dependency policy matches the full specifier and exact file, and requires a core module; bare `child_process` remains forbidden. Same-adapter neighboring files, other adapters/packages and primary/application/domain/ports/composition origins receive no new permission. This preserves subprocess construction/IPC in a secondary adapter rather than widening a role or moving driver code into composition. API owns fork options, IPC, error/exit/disconnect ordering, restart/shutdown tests and portable port wiring; composition supplies entrypoint/concurrency. Tooling tests prove the exact positive and surrounding negatives, not runtime correctness.

## Approved Next JSON builder and route signatures

`policy/validated-input` excludes the static `NextResponse.json(body, init)` response builder when the receiver is a named `NextResponse` import from `next/server` (including an import alias), resolves to the installed Next class, and calls its installed static method declaration. Genuine native static `Response.json(body, init?)` also constructs output and is excluded only after verifying the actual DOM constructor binding and method declaration; both builders require one or two arguments. This corrects the earlier mistaken rejection of native output construction without changing response class, body or status. Instance `NextRequest`/`NextResponse`/native `Response` JSON reads, shadowed/custom Response bindings and nested JSON input parsing still require concrete Zod validation. Assigning the constructor to an unrelated local binding does not create another exemption. This is not a blanket `.json()` exemption or a general custom JSON-method detection expansion.

The named-parameter route exception requires exactly a web `route.ts` basename under the existing app/presentation-app/next-http origins, an exported HTTP method (`GET`, `POST`, `PUT`, `PATCH`, `DELETE`, `HEAD`, `OPTIONS`), and exactly two parameters. The request type must resolve to the installed Next `NextRequest` class declaration (the actual Next framework contract), or the existing native `Request` from TypeScript's DOM declaration. Local lookalike names do not qualify; neighboring route-like filenames, nonroute files, non-HTTP functions, unexported functions and object methods remain checked. Reference inline/external callback exceptions are otherwise unchanged. Tests use installed Next declarations and reject unresolved imports/parser failures.

Other custom-rule adaptations preserve the reference behavior: Next route signature/static-export exceptions recognize the actual Next and migrated next-http paths; React prop ownership recognizes migrated monorepo presentation. Native-mutator tables use Maps instead of prototype-bearing objects: the reference crashed when a type was named `constructor`. A regression checks that case and that real Map mutation remains forbidden.

## Verification

- `pnpm lint:verify`: actual-config policy regressions in an isolated temporary project with real role paths; fixtures are removed, and no product source is edited.
- `pnpm typecheck:tooling`: strict TypeScript check of custom tooling.
- `pnpm lint`: whole-repository migration acceptance check.
- `pnpm typecheck`: custom tooling followed by workspace typechecks.

Policy tests reject parser errors and unknown/unresolved dependencies in direction checks, and assert exact rule IDs. They cover role directions, package/adapter isolation, aliases and the concrete DB facade, all import syntaxes, framework wrappers, exact DB migrate/seed composition entrypoints and unknown neighboring DB source, test precedence, unknown files, JavaScript add-ons, general/type/JSX rules and path-sensitive custom rules. Tests distinguish forbidden examples from valid examples. CSS policy regressions require zero lint errors/warnings for inline styles, dynamic CSS custom properties, current CSS classes and CSS Module class bindings; they check that discarded Tailwind rules/selectors are absent and unrelated JSX restrictions still reject. CI runs lint verification and root lint; Python compile checks run separately in the Python job and existing Python tests remain unchanged. The stack's isolated database environment flags, automatic test discovery, serialized workspace tests and corrected API build command are preserved.

Passing policy tests validates enforcement, **not** the product migration. Existing source violations must be fixed by their owners; they are not tooling failures or a reason to disable rules. No baseline exclusions or warning downgrades are permitted. Zod validation and mutation analysis retain the reference's conservative proof limits. Dependency audit and runtime isolation are separate concerns; this change does not claim an audit-clean graph.
