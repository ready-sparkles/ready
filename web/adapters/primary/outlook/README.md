# Ready for Outlook

Adds **Add Ready meeting** to an Outlook calendar event's organizer ribbon. The
pane opens a Ready sign-in dialog, confirms the signed-in Ready account, creates
an idempotent meeting, and prepends its join link and available dial-in details.
Existing agenda text and location are preserved. Users save/send invitations in
Outlook themselves; this add-in never sends invitations.

## Scope

- Desktop/web appointment **compose**, using an add-in-only XML manifest.
- Existing Ready Google or Microsoft sign-in works in the dialog, including signup.
  The Ready account shown in the dialog owns the meeting; the Outlook mailbox
  address is not used as an authentication assertion.
- Permission: `ReadWriteItem`, for the currently open appointment. No mailbox-wide
  Microsoft Graph or calendar OAuth permissions are added.
- `manifest.xml` provides the individual task-pane installation. The optional
  `manifest-provider.xml` uses Microsoft's online-meeting function-command
  integration to offer **Ready meeting** in the meeting compose UI when deployed
  by an admin. Both manifests use the same add-in ID; install one flavor per mailbox.
- Marketplace/default-provider recognition, native attendee Join buttons, mobile
  support, automatic synchronization, and updates on send are not included.
  Recurring invitations retain the same reusable room link.
- Requires a modern Outlook host supporting Mailbox 1.8 and DialogOrigin 1.1,
  an eligible Outlook/Exchange mailbox, and a policy allowing custom add-ins.

## Files and authentication

`manifest.xml` is generated by `manifest.mjs` with a stable add-in ID.
Its authored API is `buildManifest({ baseUrl?, isProvider? })`; CLI arguments,
UUID and generated XML stay unchanged. `build-formatter.mjs` reads the shared
`shared/domain/calendar-description.ts` implementation and emits
`web/public/outlook/calendar-description.js`. Regenerate that web-owned
artifact when changing the shared formatter; tests compare exact output.
Domain rules live in `web/domain/outlook`. Appointment and session behavior live in `web/application/outlook` behind `web/ports/outlook.ts`. Web Crypto is `web/adapters/secondary/web-crypto`. Office UI lives in this primary adapter. `web/composition/outlook` binds the crypto port. `web/scripts/build-outlook.mjs` bundles those TypeScript modules into `web/public/outlook` for the browser. Tests live in `web/tests/adapters/primary/outlook/` and exercise the TypeScript modules; a build comparison keeps the served files in sync.

```sh
corepack pnpm --filter @readymeet/web test
corepack pnpm --filter @readymeet/web lint
```

Static
HTML/JS/CSS is served by the existing web app at `/outlook/`. The dialog uses the
existing Ready web session and `/api/outlook/session` / `/api/outlook/conference`.
The latter proxies the authenticated API request to `/v1/meetings/outlook-addon`.
Only the server receives the Ready API token; the Office message contains only
conference details and a fresh per-dialog nonce. Both sender and receiver bind
the message to the Ready origin. The cookie-authenticated POST rejects missing
or foreign Origin headers and non-JSON content types.

The add-in never calls appointment `saveAsync`: saving an existing meeting can
send updates to added or removed attendees. It uses Mailbox 1.8 `getItemIdAsync`
to derive a deterministic request UUID for saved events. An `ItemNotSaved` result
uses a random UUID persisted in custom properties; other errors stop the action.
New unsaved events must not be edited concurrently in multiple windows until
Outlook persists their custom properties. Only the organizer saves/sends events.
The API namespaces this key for Outlook
and serializes creation with a PostgreSQL transaction/advisory lock. It uses the
existing calendar conference mapping table, whose historical SQL name remains
`google_addon_conferences`; no new migration is needed and Google keys/locks are
unchanged. The mapping is scoped to the authenticated Ready user.

Every click opens the authenticated dialog and revalidates the conference with
Ready. Cached item metadata is never treated as proof of an active room. Outlook
retries atomically replace a disabled room's mapping under the existing lock;
they never reactivate the disabled room. Concurrent replacements create one room.
Conference details and previous-room recovery metadata are saved before body
insertion. Retries revalidate the same mapping, and complete join URLs followed
by punctuation prevent duplicate blocks. Marked HTML blocks and exact generated
plain-text/legacy blocks are replaced while preserving surrounding agenda text.
Manually rewritten blocks may need manual removal when replacing a disabled room.
Do not store tokens in custom properties or web storage. Different Ready accounts
have separate creation keys. The dialog offers Switch
Ready account, and expired sessions offer Sign in again. Both clear the Ready
session with Auth.js CSRF protection before login; OAuth shows an account chooser.
This signs the browser out of its previous Ready session. Outlook copies
that retain custom properties intentionally retain the same reusable room.

## Deploy and sideload

Production manifests are also hosted publicly:

- Admin-deployed meeting provider: https://ready.app/outlook/manifest-provider.xml
- Individual task pane: https://ready.app/outlook/manifest.xml

Use the provider URL in Microsoft 365 admin center's custom Office Add-in upload
flow when selecting a manifest URL instead of a local file. This still requires
admin assignment and Microsoft's deployment propagation time. Hosting the XML
does not automatically update existing installations; submit manifest updates
through Microsoft 365 admin center.

After editing `manifest.mjs`, run `node web/adapters/primary/outlook/manifest.mjs --publish`
to regenerate both production manifests and their web copies, then deploy the web
app. Tests check that the hosted copies match the generator.

1. Deploy the API and web changes together (API first). Existing Google add-on
   behavior remains unchanged. No Entra scope, redirect URI, or client-secret
   change is required: authentication reuses the web application's existing
   OAuth callbacks. Publisher enrollment is separate.
2. Verify HTTPS serves `/outlook/taskpane.html`, `/outlook/dialog.html`, the JS,
   CSS and icons. Use the same web origin for the pane, dialog, and authentication.
   Do not add frame-blocking headers to the task pane. The dialog opens in a
   separate window to avoid third-party-cookie/OAuth iframe restrictions.
3. Generate a preview manifest if needed:
    ```sh
    node web/adapters/primary/outlook/manifest.mjs https://YOUR-PREVIEW-HOST /tmp/ready-outlook-preview.xml
    ```
    Production manifest targets `https://ready.app`; it isn't usable until these
    routes have actually been deployed. Local testing needs trusted HTTPS and
    working OAuth redirect configuration for the local web host.
4. Validate:
    ```sh
    npx office-addin-manifest validate web/adapters/primary/outlook/manifest.xml
    corepack pnpm --filter @readymeet/web test
    ```
5. Open https://aka.ms/olksideload in a test mailbox. Choose **My add-ins → Add a
   custom add-in → Add from File**, select the XML and review the permissions.
6. Create an appointment, open Ready from its apps/ribbon, and select **Add Ready
   meeting**. Sign in, verify the displayed Ready account, then create the meeting.

## Admin-deployed meeting provider

The provider manifest adds VersionOverrides 1.1 with one `ExecuteFunction`
appointment-organizer command, `insertReadyMeeting`, and a grayscale icon.
Its command runtime reuses the task pane's authenticated dialog and insertion
flow. It calls `event.completed({ allowEvent: true })` only after insertion
succeeds; cancellation or failure completes with `allowEvent: false`. A failed
insertion retains recovery metadata and displays an error dialog for retry.
The existing VersionOverrides 1.0 task-pane command remains a fallback.

1. Deploy the web assets, including `/outlook/commands.html`, `commands.js`,
   `meeting-flow.js`, `command-error.html`, `command-error.js`, and provider icons.
2. Generate and validate the provider manifest:
    ```sh
    node web/adapters/primary/outlook/manifest.mjs https://ready.app web/adapters/primary/outlook/manifest-provider.xml --provider
    npx office-addin-manifest validate web/adapters/primary/outlook/manifest-provider.xml
    ```
3. In Microsoft 365 admin center, deploy the custom manifest and assign it only
   to the intended test users/groups. Do not select Everyone for a mailbox test.
   An existing personal installation may need to be removed before admin deployment
   of the same ID. Microsoft documents that user-installed providers do not activate
   the replacement control; the admin can target a single user.
4. Restart Outlook, create an attendee-free event, and verify that **Ready meeting**
   appears in the online-meeting control. Test creation, cancellation, repeat use,
   preserved agenda, and save/reopen. Deployment can take time to propagate.

This is a compose-provider integration, not proof of eligibility for the recognized
partner/default-provider list. Microsoft Marketplace publication and online-meeting
registration are separate requirements for native attendee Join/Chat buttons.

## Release checks in real Outlook

- Fresh Ready signup and existing Microsoft/Google sign-in; canceled login and
  blocked popups; expired Ready session; correctly displayed host account.
- Unsaved and existing invitations; HTML and plain-text agendas; preserved
  existing text/attachments/location; save and reopen; recurring invitations.
- Repeated clicks, closed/reopened panes, canceled dialog, API timeout, failed
  custom-property save and failed body insertion: no duplicate rooms or blocks.
- A usable `https://ready.app/<code>` link, correct host rights and dial-in PIN
  when available. Delayed dial-in provisioning currently produces link-only
  details; no background invite update is promised.
- Outlook on the web, Windows, and Mac, including attendee changes on a sent
  meeting: adding Ready must not send an update. Test unsaved property persistence.
- Disabled rooms, malformed optional dial-in numbers, account switching, stale
  sessions, and non-JSON gateway errors. Invalid dial-in data yields a link-only
  invitation. Unsupported browsers see an upgrade message without executing JS.
- Automated Office mocks and manifest validation do not establish real-client
  compatibility. The task-pane version was tested in Outlook web: Google sign-in,
  insertion with dial-in, repeated use without duplicates, agenda preservation,
  and save/reopen passed. Provider and desktop client validation are separate.
